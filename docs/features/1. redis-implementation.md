# 1. Redis Implementation

## What is Redis doing in this project?

Redis serves two purposes in RideOrbit:

1. **Caching** — storing frequently read data so we don't hit the database every time
2. **Pub/Sub messaging** — a broadcast channel so WebSocket events reach clients even when
   the app is running as multiple instances

---

## How Redis connection is established (credentials flow)

You never manually create a Redis connection. Spring Boot handles it automatically:

```
docker-compose.yml
  environment:
    REDIS_HOST: redis       ← Docker service name, resolves to the redis container
    REDIS_PORT: 6379
          ↓
application.properties
  spring.data.redis.host=${REDIS_HOST}
  spring.data.redis.port=${REDIS_PORT}
          ↓
Spring Boot reads these and auto-creates a RedisConnectionFactory bean
          ↓
You declare RedisConnectionFactory as a parameter — Spring injects it for you
```

The `RedisConnectionFactory` holds the actual TCP connection to Redis.
Every Redis bean (RedisTemplate, StringRedisTemplate, RedisMessageListenerContainer)
receives this same factory — Spring wires it automatically.

### `RedisConnectionFactory` is like the Redis client in JavaScript

In JavaScript when you connect to Redis you do:

```javascript
const client = createClient({ host: 'localhost', port: 6379 })
await client.connect()

// then use it everywhere
await client.get('driver:5')
await client.publish('booking-events', json)
```

That `client` object holds the connection. You pass it around wherever you need Redis.

`RedisConnectionFactory` is the exact same idea in Spring — it holds the connection.
The difference is just how you get it:

```
JavaScript                              Spring
──────────                              ──────
you create the client yourself          Spring Boot creates RedisConnectionFactory for you
you import/pass it manually             Spring injects it wherever you declare it as a parameter
```

So instead of:
```javascript
import redisClient from './redisClient.js'
```

In Spring you just declare it as a parameter and Spring hands it to you:
```java
public RedisTemplate redisTemplate(RedisConnectionFactory connectionFactory) {
//                                 ↑ Spring sees this and injects it automatically
```

And just like in JS where you build different things on top of that client
(pub/sub, cache, etc.), in Spring you build `RedisTemplate`, `StringRedisTemplate`,
and `RedisMessageListenerContainer` — all on top of the same `RedisConnectionFactory`.

### What about password and other properties?

Currently Redis has **no password set** — it is running in open mode.
That is fine for local dev inside Docker (containers are on a private network),
but for production you would add:

```properties
# application.properties
spring.data.redis.host=${REDIS_HOST}
spring.data.redis.port=${REDIS_PORT}
spring.data.redis.password=${REDIS_PASSWORD}   # add for prod
```

```yaml
# docker-compose.yml
redis:
  command: redis-server --requirepass your_password  # enable auth on Redis itself
app:
  environment:
    REDIS_PASSWORD: your_password                    # pass it to the app
```

Spring Boot reads `spring.data.redis.password` and passes it to the connection factory
automatically — no code changes in `RedisConfig.java` needed.

| Property | Current state | Production |
|----------|--------------|------------|
| host | configured | configured |
| port | configured | configured |
| password | not set | set via env var |
| TLS/SSL | not set | enable if Redis is remote |
| database index | defaults to 0 | fine as-is |

## File: `RedisConfig.java`

```
src/main/java/com/jitendra/RideOrbit/config/RedisConfig.java
```

There are **two beans** in this file. They have completely different jobs.

---

### Bean 1 — `RedisTemplate<String, Object>`

**Job: You call it** — inject and use anywhere in the app to read/write Redis.

```java
@Bean
public RedisTemplate<String, Object> redisTemplate(RedisConnectionFactory connectionFactory) {
    RedisTemplate<String, Object> template = new RedisTemplate<>();
    template.setConnectionFactory(connectionFactory);   // give it the auto-created connection

    StringRedisSerializer stringSerializer = new StringRedisSerializer();
    template.setKeySerializer(stringSerializer);        // keys stored as plain strings: "driver:5"
    template.setHashKeySerializer(stringSerializer);

    GenericJackson2JsonRedisSerializer jsonSerializer = new GenericJackson2JsonRedisSerializer();
    template.setValueSerializer(jsonSerializer);        // values stored as JSON: {"id":5,"name":"Raj"}
    template.setHashValueSerializer(jsonSerializer);

    template.afterPropertiesSet();
    return template;
}
```

**Why serializers?**
Redis stores everything as raw bytes. Without serializers it would store garbage.
The serializers define the format:
- Keys  → plain string  e.g. `"driver:5"`
- Values → JSON         e.g. `{"id":5,"name":"Raj","isAvailable":true}`

Spring Boot also auto-creates a `StringRedisTemplate` (keys and values both as strings).
`BookingNotificationService` uses that one for publishing — no custom bean needed.

---

### Bean 2 — `RedisMessageListenerContainer`

**Job: It calls you** — runs a background thread, watches a Redis channel,
fires your listener the moment a message arrives.

```java
@Bean
public RedisMessageListenerContainer redisMessageListenerContainer(
        RedisConnectionFactory connectionFactory,
        RedisBookingEventListener bookingEventListener) {

    RedisMessageListenerContainer container = new RedisMessageListenerContainer();
    container.setConnectionFactory(connectionFactory);
    container.addMessageListener(
        bookingEventListener,                       // WHO to call when a message arrives
        new ChannelTopic("booking-events")          // WHICH channel to watch
    );
    return container;
}
```

#### What `addMessageListener` actually does — step by step

**Step 1 — Understand the TCP socket**

Your app talks to Redis over a TCP socket, same as how a browser talks to a server.
It is just a pipe between two programs where bytes flow in and out.

```
Your App ════════════ Redis
         (TCP pipe)
```

**Step 2 — Two modes of using that pipe**

Normal mode — you ask, Redis answers, done:
```
App  →  "GET driver:5"
Redis →  "{id:5, name:Raj}"
Connection is now idle
```

SUBSCRIBE mode — you register once, then just wait:
```
App  →  "SUBSCRIBE booking-events"
Redis →  "ok, registered"

... connection sits open, doing nothing ...
... connection sits open, doing nothing ...

[someone publishes]  →  Redis PUSHES the message
App receives it
```

In SUBSCRIBE mode Redis pushes to you. You do not ask again.
The connection stays open and waits indefinitely.

**Step 3 — The background thread**

Your main app thread cannot sit waiting on Redis — it has HTTP requests to handle.
So Spring creates a **separate thread** whose only job is to sit on the SUBSCRIBE
connection and wait:

```
Main Thread            Background Thread (created by Spring)
───────────            ─────────────────────────────────────
handle HTTP            blocking on redis connection... waiting...
handle HTTP            blocking on redis connection... waiting...
handle HTTP            MESSAGE ARRIVES ← Redis pushes bytes
handle HTTP            wakes up, calls onMessage()
handle HTTP            done, goes back to blocking...
```

"Blocking" means the thread is parked by the OS doing nothing — zero CPU usage —
just waiting for bytes to arrive on the socket.

**Step 4 — What `addMessageListener` does internally**

```java
container.addMessageListener(bookingEventListener, new ChannelTopic("booking-events"));
```

This does exactly 3 things:

```
1. Stores in an internal map:
   "booking-events"  →  [bookingEventListener]

2. Opens a DEDICATED TCP connection to Redis
   (separate from the one RedisTemplate uses)

3. Sends "SUBSCRIBE booking-events" on that connection
   — Redis now knows to push to this connection whenever something is published
```

Your bean method returns. The background thread is now silently waiting.

**Step 5 — Publishing a message**

```java
// BookingNotificationService does this:
redisTemplate.convertAndSend("booking-events", json);
```

This uses RedisTemplate's own TCP connection and sends:
```
PUBLISH booking-events "{\"bookingId\":5,\"status\":\"CONFIRMED\",...}"
```

Redis receives this and thinks:
- "Who subscribed to booking-events?"
- "That connection from the Spring app — push the message there."

Redis writes the bytes to the SUBSCRIBE connection.

**Step 6 — Background thread wakes up**

The thread was blocked waiting. Bytes just arrived. The OS wakes it up.
Spring's code inside the thread (simplified):

```java
while (true) {
    byte[] messageBytes = redisConnection.receive();  // thread sleeps here until Redis sends

    String channel = extractChannel(messageBytes);    // "booking-events"
    MessageListener listener = registry.get(channel); // your bookingEventListener

    listener.onMessage(message, pattern);             // YOUR METHOD IS CALLED HERE
}
```

`onMessage()` is a plain method call from that background thread. No magic.
Thread woke up → looked at the map → found your class → called the method.

**Step 7 — `onMessage()` runs**

```java
@Override
public void onMessage(Message message, byte[] pattern) {
    BookingStatusEvent event = objectMapper.readValue(message.getBody(), BookingStatusEvent.class);
    messagingTemplate.convertAndSend("/topic/booking." + event.getBookingId(), event);
}
```

Deserializes the JSON and pushes to WebSocket clients. Done.

## The two beans compared

| Bean | Who calls who | Used for |
|------|--------------|----------|
| `RedisTemplate` | **You call it** — inject and use in your service | Publishing messages, caching |
| `RedisMessageListenerContainer` | **It calls you** — fires your listener automatically | Receiving pub/sub messages |

## Full pub/sub flow (end to end)

```
PATCH /api/bookings/5/status?status=CONFIRMED
          ↓
BookingServiceImpl.updateStatus()
  → updates DB, calls:
          ↓
BookingNotificationService.notifyBookingUpdate(response)
  → builds BookingStatusEvent
  → serializes to JSON string
  → StringRedisTemplate.convertAndSend("booking-events", json)
          ↓
Redis broadcasts JSON to ALL subscribers of "booking-events"
          ↓
RedisMessageListenerContainer fires on EACH app instance
          ↓
RedisBookingEventListener.onMessage()
  → deserializes JSON back to BookingStatusEvent
  → SimpMessagingTemplate.convertAndSend("/topic/booking.5", event)
          ↓
WebSocket client (passenger/driver browser) receives:
  {
    "bookingId": 5,
    "status": "CONFIRMED",
    "message": "Driver confirmed your booking",
    "passengerId": 1,
    "driverId": 3,
    "timestamp": "2026-03-22T10:30:00"
  }
```

---

## Does `onMessage()` get called on EVERY subscriber?

**Yes — every app instance that subscribed gets called.**

Each instance opens its own SUBSCRIBE connection to Redis when it starts.
When a message is published, Redis pushes it down ALL of those connections simultaneously.
Each instance's background thread wakes up and calls its own `onMessage()`.

```
3 app instances running:

Instance 1  ══ SUBSCRIBE connection ═╗
Instance 2  ══ SUBSCRIBE connection ═╬══ Redis
Instance 3  ══ SUBSCRIBE connection ═╝

Someone publishes "booking-events"
        ↓
Redis pushes to ALL 3 connections at the same time
        ↓
All 3 instances call onMessage()
        ↓
Each instance pushes to ITS OWN connected WebSocket clients
```

This is exactly why Redis pub/sub solves the scaling problem.
Every instance gets the event, every instance notifies its own WebSocket clients,
so no client is missed regardless of which instance they are connected to.

---

## Why this matters for scaling

```
Without Redis pub/sub (in-memory STOMP broker only):

  Client A ──── connected to ──── App Instance 1
  Client B ──── connected to ──── App Instance 2

  Booking updated on Instance 2
      ↓
  Instance 2 pushes to its own in-memory STOMP broker
      ↓
  Only Client B gets notified  ✓
  Client A gets NOTHING        ✗


With Redis pub/sub:

  Booking updated on Instance 2
      ↓
  Publishes to Redis "booking-events"
      ↓
  Redis pushes to ALL instances (1 and 2)
      ↓
  Both instances push to their own WebSocket clients
      ↓
  Both Client A and Client B get notified  ✓
```

## Simple summary (the whole thing in plain words)

- **RedisTemplate bean** — just sets up the connection so you can interact with Redis
  from anywhere in the app. Use it to publish messages or read/write cache entries.

- **RedisMessageListenerContainer** — a completely separate connection that runs on its
  own background thread and keeps listening forever. Nothing to do with RedisTemplate.

- **You can add as many `addMessageListener()` calls as you want** — each one registers
  a different listener for a different channel. They all share the same background thread
  and the same internal map:
  ```
  "booking-events"      →  RedisBookingEventListener
  "driver-location"     →  DriverLocationListener      (if you add one)
  "payment-events"      →  PaymentListener             (if you add one)
  ```

- **When someone publishes to a channel**, Redis pushes the message to the SUBSCRIBE
  connection. The background thread wakes up, looks up the channel in the map, finds
  the right listener, and calls `.onMessage()` on it automatically.

```
publish("booking-events", json)
          ↓
Redis pushes to SUBSCRIBE connection
          ↓
Background thread wakes up
          ↓
registry.get("booking-events") → RedisBookingEventListener
          ↓
.onMessage() called automatically
```

That is the entire mechanism. No magic — just a map lookup and a method call.
