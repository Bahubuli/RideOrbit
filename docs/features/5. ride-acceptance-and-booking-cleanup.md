# 5. Ride Acceptance and Booking Cleanup

## What this document covers

Three related changes happened together:

1. **Busy drivers can now receive ride requests** — the `isAvailable` filter was removed
2. **The acceptance flow was built** — driver accepts a ride request, booking is created automatically
3. **The booking layer was cleaned up** — removed endpoints and methods that belonged to a different booking model

These are all connected. Once busy drivers can accept rides, the old availability
system becomes dead code. And once the acceptance flow creates bookings internally,
the old manual `POST /api/bookings` endpoint becomes dead code too.

---

## Change 1 — Busy drivers can receive ride requests

### What changed

Previously, `getNearbyDrivers()` in `LocationServiceImpl` checked the `isAvailable`
flag in each driver's Redis hash and skipped anyone with `isAvailable = false`:

```java
// BEFORE — inside getNearbyDrivers()
Object availableObj = redisTemplate.opsForHash().get(dataKey, "isAvailable");
if ("false".equals(availableObj != null ? availableObj.toString() : null)) {
    continue;   // skip — on an active booking
}
```

This filter was **removed**. Now `getNearbyDrivers()` returns all online drivers
regardless of whether they are on an active booking:

```java
// AFTER — inside getNearbyDrivers()
// Only skip if the data hash has expired (driver went offline)
if (!Boolean.TRUE.equals(redisTemplate.hasKey(dataKey))) {
    continue;
}
// isAvailable is NOT checked — busy drivers can still accept new requests
```

### Why this matters

In the real world, a driver finishing a ride at 28th Street can accept a new
passenger at 30th Street. They are 2 minutes away from being free. The previous
flow made them invisible until their current ride was marked COMPLETED — by which
time the new passenger may have waited 5+ minutes for someone farther away.

### What became dead code as a result

Once `getNearbyDrivers()` stopped reading `isAvailable`, everything that **wrote**
to that flag became dead code:

| What wrote `isAvailable` | Where | Status |
|---|---|---|
| `saveDriverLocation()` — set `true` on first entry | `LocationServiceImpl` | **Removed** |
| `updateDriverAvailability()` — set true/false | `LocationService` interface + impl | **Removed** |
| `BookingServiceImpl` — called `updateDriverAvailability()` 6 times | `BookingServiceImpl` | **Removed** |
| `BookingServiceImpl` — called `driver.setIsAvailable(false)` in DB | `BookingServiceImpl` | **Removed** |
| `isAvailable` check in `create()` | `BookingServiceImpl` | **Removed** |

The `isAvailable` field still exists in the Redis hash and on the Driver entity.
Nothing writes to it anymore, but nothing breaks if old data has it — the value is
just ignored.

### Files changed

```
LocationServiceImpl.java  — removed isAvailable filter from getNearbyDrivers()
                          — removed isAvailable write from saveDriverLocation()
                          — removed updateDriverAvailability() method

LocationService.java      — removed updateDriverAvailability() from interface

BookingServiceImpl.java   — removed isAvailable check in create()
                          — removed all locationService.updateDriverAvailability() calls
                          — removed LocationService dependency entirely
                          — removed driver.setIsAvailable() DB writes
```

## Change 2 — The acceptance flow

### The problem with the old booking creation

The old flow expected the **driver's client** to call `POST /api/bookings` with a
full `BookingRequest` body:

```json
{
  "passengerId": 1,
  "driverId": 5,
  "pickupLocation": "MG Road",
  "dropoffLocation": "Airport",
  "fare": 450
}
```

But in the Uber-style flow, the driver just taps "Accept" on a notification.
The system already has all the ride details from when the passenger submitted
the ride request. The driver should not need to re-enter any of that.

### The new flow

```
Driver sees ride request notification in their app (includes estimatedFare)
    ↓
Taps "Accept"
    ↓
POST /api/ride-requests/{rideRequestId}/accept?driverId=5
    ↓
System looks up the stored ride request (has all passenger/location/fare details)
    ↓
Creates booking with status CONFIRMED (fare from stored request — no recalculation)
    ↓
Passenger notified via WebSocket (/topic/passenger.{passengerId}.ride-updates)
    ↓
Other notified drivers dismissed via WebSocket (status: "TAKEN")
    ↓
Driver receives BookingResponse back
```

The driver sends **one parameter** — their own ID. Everything else comes from
the stored ride request.

---

### Step by step — what `acceptRide()` does

**Step 1 — Driver sends one request:**

```
POST /api/ride-requests/f3a2c1d0.../accept?driverId=5
```

That's it. Just the ride request ID (from the notification they received) and
their own ID. No passenger details, no addresses, no fare.

**Step 2 — System retrieves everything from Redis (and deletes it atomically):**

```
Redis GETDEL "ride-request:pending:f3a2c1d0..."
    ↓
Returns the stored PendingRideRequest:
  passengerId: 1
  pickupAddress: "Connaught Place"
  dropoffAddress: "Noida Sector 18"
  pickupLat/Lng, dropoffLat/Lng
  estimatedFare: 380.00
  notifiedDriverIds: [5, 12, 7]
    ↓
Key is DELETED from Redis in the same operation
(no other driver can accept this ride now)
```

**Step 3 — Booking is created directly (no DTO, no mapper):**

The fare was already calculated at ride request time and stored in the
`PendingRideRequest`. No recalculation needed — the passenger was quoted
this price when they requested the ride.

```java
Booking.builder()
    .passenger(passenger)      // from DB lookup using stored passengerId
    .driver(driver)            // from DB lookup using driverId from request
    .pickupLocation("Connaught Place")   // from stored ride request
    .dropoffLocation("Noida Sector 18") // from stored ride request
    .fare(pending.getEstimatedFare())    // from stored ride request (calculated at request time)
    .status(CONFIRMED)         // always — a driver is present
    .build();
```

**Step 4 — Passenger is notified via WebSocket:**

```
BookingNotificationService → /topic/passenger.1.ride-updates
    ↓ RabbitMQ → WebSocket
Passenger browser receives:
  { bookingId: 42, status: "CONFIRMED", driverId: 5, message: "Driver confirmed your booking" }
```

The passenger subscribes to `/topic/passenger.1.ride-updates` once when they
open the app. Every booking event (CONFIRMED, IN_PROGRESS, COMPLETED, CANCELLED)
arrives on this same topic. No need to dynamically subscribe to a per-booking topic.

The driver also receives the same event on `/topic/driver.5.ride-updates`.

**Step 5 — Other drivers are dismissed:**

```
For each notified driver except the one who accepted:
  → /topic/driver.12.ride-request  →  { status: "TAKEN", rideRequestId: "f3a2c1d0..." }
  → /topic/driver.7.ride-request   →  { status: "TAKEN", rideRequestId: "f3a2c1d0..." }
```

**Step 6 — Driver gets the BookingResponse back:**

```json
{
  "id": 42,
  "passengerId": 1,
  "driverId": 5,
  "pickupLocation": "Connaught Place",
  "dropoffLocation": "Noida Sector 18",
  "fare": 380.00,
  "status": "CONFIRMED"
}
```

### How ride requests are stored — Redis

When `requestRide()` runs, after notifying all nearby drivers, it stores the
ride request in Redis as a JSON value with a 5-minute TTL:

```java
String key = "ride-request:pending:" + rideRequestId;
redisTemplate.opsForValue().set(key, pending, 5, TimeUnit.MINUTES);
```

```
Redis key:  "ride-request:pending:f3a2c1d0-..."
Type:       string (JSON-serialized PendingRideRequest)
TTL:        5 minutes

Value (JSON):
{
  "rideRequestId": "f3a2c1d0-...",
  "passengerId": 1,
  "pickupLatitude": 28.6139,
  "pickupLongitude": 77.2090,
  "pickupAddress": "Connaught Place, Delhi",
  "dropoffLatitude": 28.5355,
  "dropoffLongitude": 77.3910,
  "dropoffAddress": "Noida Sector 18",
  "estimatedFare": 380.00,
  "notifiedDriverIds": [5, 12, 7],
  "timestamp": "2026-03-22T10:30:00"
}
```

### Why Redis and not in-memory?

| Requirement | In-memory (ConcurrentHashMap) | Redis |
|---|---|---|
| Survives app restart | No — all pending requests lost | Yes |
| Works with multiple instances | No — each instance has its own map | Yes — shared external store |
| Auto-expiry (no driver accepts) | Manual cleanup needed | TTL handles it — key deletes itself |
| Race condition safety | Thread-safe within one JVM | Atomic across all instances (GETDEL) |

With a `ConcurrentHashMap`, if Instance A stores a ride request but the driver's
accept hits Instance B (load balancer routing), the lookup fails with "not found".
Redis is shared by all instances — any instance can store, any instance can accept.

### Auto-expiry with TTL

If no driver accepts within 5 minutes, the Redis key expires automatically.
No background cleanup job needed, no memory leak. The passenger sees `SEARCHING`
and can request again.

```
requestRide() stores key with TTL = 5 min
    ↓
3 min later: driver accepts → GETDEL succeeds → booking created
    OR
5 min later: no accept → Redis auto-deletes the key → request expired
```

### How only one driver can accept — the race condition solution

```java
String key = RIDE_REQUEST_KEY_PREFIX + rideRequestId;
PendingRideRequest pending = (PendingRideRequest) redisTemplate.opsForValue().getAndDelete(key);
if (pending == null) {
    throw new IllegalArgumentException("Ride request not found or already accepted");
}
```

`getAndDelete()` maps to Redis `GETDEL` — a **single atomic command**. It returns
the value and deletes the key in one operation. If two drivers on different app
instances tap "Accept" at the same millisecond:

```
Driver 5 (Instance A):  GETDEL "ride-request:pending:f3a2c1d0" → gets the JSON ✓
Driver 7 (Instance B):  GETDEL "ride-request:pending:f3a2c1d0" → gets nil ✗

Driver 5 proceeds to create booking
Driver 7 gets "already accepted" error
```

Redis processes commands sequentially (single-threaded for command execution).
Only one `GETDEL` can succeed — the second one sees the key already gone.
This works regardless of how many app instances are running.

Note: we no longer need the pessimistic lock (`findByIdForUpdate`) that the old
`create()` used. That lock prevented two passengers from booking the same driver
simultaneously. With `GETDEL`, only one accept wins per ride request — and we
now allow drivers to have multiple concurrent bookings, so there is no
availability check to protect.

### How fare is calculated

The fare is calculated at **ride request time** — when the passenger submits
pickup and dropoff coordinates. This way the passenger sees the estimated fare
immediately, drivers see it in the notification, and the same fare carries
through to the booking when a driver accepts. No recalculation at acceptance time.

```java
private BigDecimal calculateFare(double pickupLat, double pickupLng,
                                 double dropoffLat, double dropoffLng) {
    // Haversine formula — straight-line distance between two coordinates
    double R = 6371; // Earth radius in km
    double dLat = Math.toRadians(dropoffLat - pickupLat);
    double dLon = Math.toRadians(dropoffLng - pickupLng);
    double a = Math.sin(dLat / 2) * Math.sin(dLat / 2)
            + Math.cos(Math.toRadians(pickupLat)) * Math.cos(Math.toRadians(dropoffLat))
            * Math.sin(dLon / 2) * Math.sin(dLon / 2);
    double c = 2 * Math.atan2(Math.sqrt(a), Math.sqrt(1 - a));
    double distanceKm = R * c;

    // base fare + rate per km
    return BigDecimal.valueOf(50.0 + distanceKm * 15.0)
            .setScale(2, RoundingMode.HALF_UP);
}
```

```
Base fare:   Rs 50
Rate per km: Rs 15
Example:     Connaught Place → Noida Sector 18 ≈ 22 km
             50 + (22 × 15) = Rs 380.00
```

This is straight-line distance, not road distance. For a real app you would
use a routing API (Google Directions, OSRM). But for the core booking flow,
this is enough to fill the `fare` column in the database.

### How the booking is created

After removing the ride request from Redis and looking up the driver:

```java
Booking booking = Booking.builder()
        .passenger(passenger)
        .driver(driver)
        .pickupLocation(pending.getPickupAddress())
        .dropoffLocation(pending.getDropoffAddress())
        .fare(pending.getEstimatedFare())       // calculated at request time
        .status(Booking.BookingStatus.CONFIRMED)
        .build();

Booking saved = bookingRepository.save(booking);
```

Key points:
- Status is always `CONFIRMED` — a driver is always present (they just accepted)
- `PENDING` status is never created in the Uber flow
- No `BookingRequest` DTO needed — the entity is built directly from the stored ride request
- No `BookingMapper.toEntity()` needed — that mapper method was removed

The `BookingMapper.toResponse()` is still used to convert the saved entity to a
`BookingResponse` for the API response and WebSocket notification.

### How the passenger and driver are notified

```java
BookingResponse response = bookingMapper.toResponse(saved);
notificationService.notifyBookingUpdate(response);
```

`BookingNotificationService` pushes the same `BookingStatusEvent` to two personal topics:

```
/topic/passenger.{passengerId}.ride-updates   ← passenger receives
/topic/driver.{driverId}.ride-updates         ← driver receives
```

```json
{
  "bookingId": 42,
  "status": "CONFIRMED",
  "message": "Driver confirmed your booking",
  "passengerId": 1,
  "driverId": 5,
  "timestamp": "2026-03-22T10:31:00"
}
```

Both the passenger and driver subscribe to their own personal topic **once**
when they open the app. Every booking event (CONFIRMED, IN_PROGRESS, COMPLETED,
CANCELLED) arrives on the same topic. No need to know the `bookingId` in advance
and no need to dynamically subscribe after acceptance.

```
Passenger opens app → subscribes to /topic/passenger.1.ride-updates
Driver opens app    → subscribes to /topic/driver.5.ride-updates

All booking events for that user arrive on their personal topic:
  ride accepted, ride started, ride completed, ride cancelled
```

### Why personal topics instead of per-booking topics?

The old approach used `/topic/booking.{bookingId}`. The problem:

```
Passenger requests ride → gets rideRequestId (no bookingId yet)
    ↓
Can't subscribe to /topic/booking.??? — booking doesn't exist
    ↓
Driver accepts → booking 42 created → pushes to /topic/booking.42
    ↓
Nobody is listening ✗
```

The booking ID only exists **after** a driver accepts. The passenger has no way
to subscribe to it before that. Personal topics solve this — the passenger knows
their own ID before anything happens.

### How other drivers are dismissed

After the booking is created, every other driver who was notified for this ride
request receives a dismissal on their ride request topic:

```java
for (Long notifiedDriverId : pending.notifiedDriverIds) {
    if (!notifiedDriverId.equals(driverId)) {
        messagingTemplate.convertAndSend(
                "/topic/driver." + notifiedDriverId + ".ride-request",
                Map.of(
                        "rideRequestId", rideRequestId,
                        "status", "TAKEN",
                        "message", "This ride has been accepted by another driver"
                )
        );
    }
}
```

The driver's client receives this on the same topic as ride request notifications.
The client code checks the `status` field to distinguish between a new request
and a dismissal:

```javascript
client.subscribe('/topic/driver.7.ride-request', (frame) => {
    const data = JSON.parse(frame.body)

    if (data.status === 'TAKEN') {
        // remove the ride request card from the UI
        dismissRideRequest(data.rideRequestId)
    } else {
        // show new ride request notification
        showRideRequest(data)
    }
})
```

### The full picture — ride request to ride completion

This is the entire lifecycle of a ride in four API calls:

```
STEP 1 — Passenger requests a ride
──────────────────────────────────
POST /api/ride-requests
{ passengerId:1, pickupLat:28.61, pickupLng:77.20, dropoffLat:28.53, dropoffLng:77.39, ... }
        ↓
    Calculate fare from Haversine distance → Rs 380.00
    Redis GEORADIUS → find drivers within 5 km
    Notify each nearby driver via WebSocket (includes estimatedFare)
    Store PendingRideRequest in Redis (TTL 5 min, includes estimatedFare)
        ↓
    Passenger gets: { rideRequestId:"f3a2c1d0...", estimatedFare:380.00, driversNotified:3, status:"SEARCHING" }
    Drivers 5, 12, 7 each receive a RideRequestNotification with estimatedFare on their WebSocket topic


STEP 2 — Driver accepts
────────────────────────
POST /api/ride-requests/f3a2c1d0.../accept?driverId=5
        ↓
    Redis GETDEL → retrieve + delete PendingRideRequest (atomic)
    Create Booking in DB (status: CONFIRMED, fare from stored request)
        ↓
    Passenger notified:  /topic/passenger.1.ride-updates → { bookingId:42, status:"CONFIRMED" }
    Driver 5 notified:   /topic/driver.5.ride-updates    → { bookingId:42, status:"CONFIRMED" }
    Driver 12 dismissed: /topic/driver.12.ride-request   → { status:"TAKEN" }
    Driver 7 dismissed:  /topic/driver.7.ride-request    → { status:"TAKEN" }
    Driver 5 gets: BookingResponse { id:42, fare:380.00, status:"CONFIRMED" }


STEP 3 — Driver picks up passenger
───────────────────────────────────
PATCH /api/bookings/42/status?status=IN_PROGRESS
        ↓
    Records actualPickupTime in DB
    Passenger notified: /topic/passenger.1.ride-updates → { bookingId:42, status:"IN_PROGRESS" }
    Driver notified:    /topic/driver.5.ride-updates    → { bookingId:42, status:"IN_PROGRESS" }


STEP 4 — Ride completes
────────────────────────
PATCH /api/bookings/42/status?status=COMPLETED
        ↓
    Records completedAt in DB
    Passenger notified: /topic/passenger.1.ride-updates → { bookingId:42, status:"COMPLETED" }
    Driver notified:    /topic/driver.5.ride-updates    → { bookingId:42, status:"COMPLETED" }

                    OR (if cancelled at any point)

PATCH /api/bookings/42/status?status=CANCELLED
        ↓
    Passenger notified: /topic/passenger.1.ride-updates → { bookingId:42, status:"CANCELLED" }
    Driver notified:    /topic/driver.5.ride-updates    → { bookingId:42, status:"CANCELLED" }
```

## Change 3 — Booking layer cleanup

### What was removed from `BookingController`

The old controller had 7 endpoints. Now it has 4:

| Endpoint | Before | After | Why |
|---|---|---|---|
| `GET /{id}` | Yes | **Yes** | Passenger/driver checking current booking |
| `GET /passenger/{id}` | Yes | **Yes** | Ride history for passenger |
| `GET /driver/{id}` | Yes | **Yes** | Ride history for driver |
| `PATCH /{id}/status` | Yes | **Yes** | Ride lifecycle: CONFIRMED → IN_PROGRESS → COMPLETED / CANCELLED |
| `POST /` | Yes | **Removed** | Bookings are now created internally by `acceptRide()` |
| `PUT /{id}` | Yes | **Removed** | Driver swap logic — does not exist in Uber flow |
| `DELETE /{id}` | Yes | **Removed** | You cancel a ride with status update, not delete |
| `GET /` (list all) | Yes | **Removed** | Admin endpoint, not part of any user flow |

### What was removed from `BookingServiceImpl`

| Method | Status | Reason |
|---|---|---|
| `create()` | **Removed** | Bookings are created by `RideRequestServiceImpl.acceptRide()` |
| `update()` | **Removed** (earlier) | Driver swap logic, no longer applicable |
| `deleteById()` | **Removed** | Cancellation is a status update, not a delete |
| `findAll()` | **Removed** | No endpoint exposes it |
| `findById()` | Kept | |
| `findByPassengerId()` | Kept | |
| `findByDriverId()` | Kept | |
| `updateStatus()` | Kept | |

### What was removed from `BookingMapper`

| Method | Status | Reason |
|---|---|---|
| `toEntity()` | **Removed** | Used by old `create()` — the acceptance flow builds the entity directly |
| `updateEntity()` | **Removed** | Used by old `update()` — driver swap is gone |
| `toResponse()` | Kept | Used by all read methods and by `acceptRide()` |

### Interfaces cleaned up

```
BookingWriteService:
  BEFORE:  create(), update(), updateStatus(), deleteById()
  AFTER:   updateStatus()

BookingReadService:
  BEFORE:  findById(), findAll(), findByPassengerId(), findByDriverId()
  AFTER:   findById(), findByPassengerId(), findByDriverId()
```

### Why `PENDING` status is now dead

`PENDING` was set when a booking was created without a driver — the mapper decided:

```java
BookingStatus status = driver != null ? CONFIRMED : PENDING;
```

In the Uber flow, bookings are only created when a driver accepts. A driver is
always present at creation time. So status is always `CONFIRMED`. No booking
ever enters `PENDING` state.

The `PENDING` enum value still exists on the `Booking` entity. Removing it would
require a database migration to drop the enum value from the `bookings.status`
column — not worth it for a value that is simply never used.

### The status lifecycle now

```
CONFIRMED ──→ IN_PROGRESS ──→ COMPLETED
    │
    └────────────────────────→ CANCELLED
```

| Status | When it's set | Side effect |
|---|---|---|
| `CONFIRMED` | Driver accepts ride request | Booking created |
| `IN_PROGRESS` | Driver picked up the passenger | `actualPickupTime` recorded |
| `COMPLETED` | Ride finished | `completedAt` recorded |
| `CANCELLED` | Booking cancelled at any point | None |

No driver availability toggling on any transition — that system is gone.
