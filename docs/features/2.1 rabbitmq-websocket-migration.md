# 2.1 RabbitMQ WebSocket Migration

## What is a Message Broker?

A message broker is a middleman between services that sends and receives messages.
Instead of Service A talking directly to Service B, both talk to the broker.

```
Without broker:                     With broker:
───────────────                     ────────────
Service A ──► Service B             Service A ──► Broker ──► Service B
                                                         ──► Service C
                                                         ──► Service D
```

The broker's job:
- **Receive** messages from publishers
- **Store** them temporarily (in queues)
- **Route** them to the right subscribers
- **Deliver** them when the subscriber is ready

---

## What is RabbitMQ?

RabbitMQ is a message broker. It implements two protocols:

**AMQP** (Advanced Message Queuing Protocol) — port 5672
The main protocol. Used for service-to-service messaging, task queues, etc.

**STOMP** (Simple Text Oriented Messaging Protocol) — port 61613
A simpler text-based protocol. This is the one Spring WebSocket uses.
We enable it via the `rabbitmq_stomp` plugin.

```
RabbitMQ
  ├── AMQP  :5672   ← general purpose messaging (not used here yet)
  ├── STOMP :61613  ← what Spring WebSocket relay connects to
  └── HTTP  :15672  ← management UI (browser)
```

### Core concepts inside RabbitMQ

**Exchange** — receives messages and decides where to route them.
Think of it as a post office sorting room.

**Queue** — holds messages until a consumer picks them up.
Think of it as a mailbox.

**Binding** — a rule that connects an exchange to a queue.
Think of it as the address label.

**Consumer** — subscribes to a queue and receives messages from it.
In our case, the WebSocket clients are the consumers.

```
Publisher
    │
    │ sends message to
    ▼
Exchange
    │
    │ routes based on binding rules
    ▼
Queue ──► Consumer (WebSocket client)
```

When a browser subscribes to `/topic/booking.5` via STOMP,
RabbitMQ automatically creates a queue for that subscription
and binds it to the topic exchange. The browser becomes the consumer of that queue.

## Why we migrated from Redis pub/sub + in-memory broker to RabbitMQ

### What we had before

```
BookingService
    → BookingNotificationService
        → Redis pub/sub ("booking-events" channel)
            → RedisBookingEventListener.onMessage() on each instance
                → SimpMessagingTemplate → in-memory STOMP broker
                    → WebSocket clients
```

Redis pub/sub solved the multi-instance problem — every instance got the event.
But the in-memory STOMP broker still had these problems:

| Problem | Impact |
|---|---|
| Subscriptions stored in RAM | Lost on app restart — clients must reconnect and re-subscribe |
| No message persistence | Client offline when message sent = message lost forever |
| No acknowledgement | No way to know if client actually received it |
| Memory pressure | 10,000 users = 10,000 open connections + 10,000 HashMap entries per instance |

### What we have now

```
BookingService
    → BookingNotificationService
        → SimpMessagingTemplate → RabbitMQ STOMP relay
            → RabbitMQ (central broker, shared by all instances)
                → WebSocket clients on any instance
```

RabbitMQ replaces BOTH Redis pub/sub AND the in-memory broker in one shot.
Redis stays in the project but only for caching now.

---

## How RabbitMQ fixes each problem

**Subscriptions lost on restart:**
RabbitMQ stores subscriptions externally. When the app restarts it reconnects to
RabbitMQ and clients re-subscribe — no data lost from RabbitMQ's side.

**Messages lost when client is offline:**
RabbitMQ queues hold messages until the client reconnects and drains them.
With the in-memory broker the message was gone the moment the client disconnected.

**No acknowledgement:**
RabbitMQ supports message acknowledgement — it knows if a message was delivered
and can retry if not.

**Cross-instance broadcasting:**
RabbitMQ is a central external broker shared by all instances.
No need for Redis pub/sub to bridge instances — RabbitMQ does this natively.

## How the STOMP relay connection works

Each app instance maintains two permanent TCP connections to RabbitMQ on port 61613:

```
Instance A
┌─────────────────────────────────────────┐
│                                         │
│  System Connection (one per instance)   │──────────────┐
│  used to SEND messages to RabbitMQ      │              │
│                                         │         TCP :61613
│  Client Connection (one per browser)    │──────────────┤
│  used when a browser subscribes         │              │
│  e.g. browser does SUBSCRIBE            │              ▼
│  /topic/booking.5 → relay forwards      │         RABBITMQ
│  that subscription to RabbitMQ          │
│                                         │
└─────────────────────────────────────────┘
```

**System connection** — Spring uses this to publish messages.
When `messagingTemplate.convertAndSend("/topic/booking.5", event)` is called,
Spring sends it down this connection to RabbitMQ.

**Client connection** — When a browser connects and does `SUBSCRIBE /topic/booking.5`,
the relay forwards that subscription to RabbitMQ.
RabbitMQ now knows this browser is interested in `/topic/booking.5`.

## What RabbitMQ stores internally

RabbitMQ maintains a subscription registry externally — not in any app's RAM:

```
RabbitMQ subscription registry:
┌────────────────────────────────────────────────────────────┐
│  /topic/booking.5  →  [Client1(A), Client2(A), Client3(B)] │
│  /topic/booking.9  →  [Client4(B)]                         │
│  /topic/booking.12 →  [Client1(A)]                         │
└────────────────────────────────────────────────────────────┘
```

This lives inside RabbitMQ — not inside Instance A or B.
If Instance A restarts, RabbitMQ still has the registry.
Clients on Instance A just reconnect and re-subscribe.

## What changed in the code

### Files removed
- `RedisBookingEventListener.java` — no longer needed, RabbitMQ handles delivery
- `RedisMessageListenerContainer` bean removed from `RedisConfig.java`

### Files changed
- `WebSocketConfig.java` — switched from `enableSimpleBroker` to `enableStompBrokerRelay`
- `BookingNotificationService.java` — removed Redis, now uses `SimpMessagingTemplate` directly
- `RedisConfig.java` — removed pub/sub listener container, Redis kept for caching only
- `application.properties` — added RabbitMQ connection config
- `docker-compose.yml` — added RabbitMQ service with STOMP plugin
- `build.gradle` — added `reactor-netty` dependency for STOMP relay TCP connection

---

## Why reactor-netty dependency is needed

`enableStompBrokerRelay` uses reactor-netty under the hood to create and manage
the TCP connection from Spring to RabbitMQ's STOMP port.
Without it the relay cannot establish the connection and the app will fail to start.

---

## What Redis does now

Redis is still running — but only for caching:

```
GET /api/drivers/5
      │
      ├── check Redis first
      │     hit?  → return cached driver, no DB call
      │     miss? → query DB, store in Redis, return
      ▼
  Postgres
```

Zero involvement in WebSocket or notifications anymore.

- See which clients are connected and subscribed
