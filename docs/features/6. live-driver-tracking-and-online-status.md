# 6. Live Driver Tracking and Online Status

## What was missing

After a driver accepted a ride, the passenger had no way to see where the driver was.

The driver was already sending GPS coordinates every 3-5 seconds over WebSocket —
that data landed in Redis and stopped there. Nothing pushed it onward to the passenger.

Two things were added:

1. **Live driver location tracking** — when a driver has an active ride, every location
   update they send is forwarded in real time to the passenger's WebSocket topic
2. **Explicit online/offline endpoints** — so a driver can cleanly signal when they start
   or end their shift, rather than relying purely on Redis TTL expiry

---

## Feature 1 — Live driver location for passengers

### How it works

The driver's app already sends location via WebSocket every 3-5 seconds:

```
Driver app → STOMP /app/driver/location → LocationMessageController
```

Before this change, `LocationMessageController` only called `saveDriverLocation()` and returned.

Now, after saving, it checks whether the driver has an active booking:

```java
bookingService.findActiveByDriverId(request.getDriverId())
    .ifPresent(booking -> {
        messagingTemplate.convertAndSend(
            "/topic/passenger." + booking.getPassengerId() + ".driver-location",
            location
        );
    });
```

An active booking means status is `CONFIRMED` or `IN_PROGRESS`. If the driver has no active
booking (waiting for a ride, or finished), nothing is pushed — no unnecessary traffic.

### What the passenger receives

The passenger subscribes to their personal tracking topic once after a booking is confirmed:

```javascript
client.subscribe('/topic/passenger.1.driver-location', (frame) => {
    const location = JSON.parse(frame.body)
    // update driver pin on map
    updateMapMarker(location.latitude, location.longitude)
})
```

Payload (`DriverLocationResponse`):

```json
{
  "driverId": 5,
  "latitude": 28.6139,
  "longitude": 77.2090,
  "lastUpdated": "2026-03-26T10:31:05"
}
```

This arrives every 3-5 seconds for as long as the driver is on an active ride.

### When tracking stops

The passenger stops receiving location pushes when:

- Driver's booking status moves to `COMPLETED` or `CANCELLED`
- `findActiveByDriverId()` returns empty → no push happens

The passenger does not need to unsubscribe manually. Messages simply stop arriving.

### Full flow

```
Driver app
    │
    │ sends GPS every 3-5s via WebSocket
    ▼
/app/driver/location
    │
    ▼
LocationMessageController.updateDriverLocation()
    │
    ├── locationService.saveDriverLocation()
    │       ↓
    │   Redis: update geo index + data hash
    │
    └── bookingService.findActiveByDriverId(driverId)
            │
            ├── no active booking → nothing pushed
            │
            └── active booking found (CONFIRMED or IN_PROGRESS)
                    │
                    ▼
            messagingTemplate → /topic/passenger.{passengerId}.driver-location
                    │
                    ↓ RabbitMQ → WebSocket
            Passenger app receives DriverLocationResponse
            Updates driver position on map
```

### What changed

**`BookingRepository`** — new query method:

```java
Optional<Booking> findByDriver_IdAndStatusIn(Long driverId, List<Booking.BookingStatus> statuses);
```

Spring Data JPA derives this from the method name:
- `findBy` — select
- `Driver_Id` — join to driver, match on id
- `AndStatusIn` — AND status is one of the provided list

**`BookingReadService`** — new interface method:

```java
Optional<BookingResponse> findActiveByDriverId(Long driverId);
```

**`BookingServiceImpl`** — implementation:

```java
public Optional<BookingResponse> findActiveByDriverId(Long driverId) {
    return bookingRepository.findByDriver_IdAndStatusIn(
            driverId,
            List.of(Booking.BookingStatus.CONFIRMED, Booking.BookingStatus.IN_PROGRESS)
    ).map(bookingMapper::toResponse);
}
```

**`LocationMessageController`** — now injects `BookingService` and `SimpMessagingTemplate`.
After saving location, checks for active booking and conditionally pushes to passenger.

## Feature 2 — Driver online/offline

### The problem before

Drivers had no explicit way to go online or offline. The only way into Redis was through
WebSocket location updates. The only way out was the 6-hour TTL expiry.

This meant:
- A driver starting their shift had to send a location update first before being discoverable
- A driver ending their shift just... stopped sending location and disappeared after 6 hours
- No way for the system to know a driver intentionally went offline vs just lost connection

### The new endpoints

**Go online**

```
POST /api/drivers/{id}/online?latitude=28.6139&longitude=77.2090
```

Driver calls this when they open the app and are ready to take rides. Sets their initial
position in Redis immediately — they are discoverable for ride requests from this moment.

```
Response 200:
{
  "driverId": 5,
  "latitude": 28.6139,
  "longitude": 77.2090,
  "lastUpdated": "2026-03-26T10:30:00"
}
```

After going online, the driver switches to WebSocket for ongoing location updates.
HTTP is only used for this initial signal.

**Go offline**

```
POST /api/drivers/{id}/offline
```

Driver calls this when they end their shift. Removes them from:
- The Redis geo index (`driver:location:geo`) — no longer found by GEORADIUS
- Their data hash (`driver:location:data:{id}`) — no longer appears as online

```
Response 204 No Content
```

### When to use each

| Event | Endpoint |
|---|---|
| Driver opens app, starts shift | `POST /api/drivers/5/online?latitude=...&longitude=...` |
| Driver sends GPS every 3-5s | WebSocket `/app/driver/location` |
| Driver ends shift | `POST /api/drivers/5/offline` |
| Driver app crashes / loses signal | TTL expires after 6 hours (fallback) |

The online/offline endpoints are the intentional path. TTL expiry is the fallback for
unintentional disconnections.

### What changed

**`DriverController`** — two new endpoints added:

```java
@PostMapping("/{id}/online")
public ResponseEntity<DriverLocationResponse> goOnline(
        @PathVariable Long id,
        @RequestParam Double latitude,
        @RequestParam Double longitude) {
    DriverLocationRequest request = new DriverLocationRequest(id, latitude, longitude);
    DriverLocationResponse response = locationService.saveDriverLocation(request);
    return ResponseEntity.ok(response);
}

@PostMapping("/{id}/offline")
public ResponseEntity<Void> goOffline(@PathVariable Long id) {
    locationService.removeDriverLocation(id);
    return ResponseEntity.noContent().build();
}
```

Both delegate directly to the existing `LocationService` methods — `saveDriverLocation()`
and `removeDriverLocation()` — which already existed and handled Redis correctly.

No new service methods were needed.

## WebSocket topics — updated reference

| Topic | Direction | Who subscribes | Content |
|---|---|---|---|
| `/topic/driver.{id}.ride-request` | Server → Driver | Driver | New ride request notification |
| `/topic/driver.{id}.ride-updates` | Server → Driver | Driver | Booking status changes |
| `/topic/passenger.{id}.ride-updates` | Server → Passenger | Passenger | Booking status changes |
| `/topic/passenger.{id}.driver-location` | Server → Passenger | Passenger | **Live driver GPS (new)** |
| `/app/driver/location` | Driver → Server | — | Driver sends GPS update |

## Full ride lifecycle with tracking

```
STEP 1 — Driver goes online
───────────────────────────
POST /api/drivers/5/online?latitude=28.6139&longitude=77.2090
    ↓
Driver added to Redis geo index — discoverable for ride requests


STEP 2 — Passenger requests ride
──────────────────────────────────
POST /api/ride-requests
    ↓
Redis GEORADIUS finds Driver 5 within 5km
Driver 5 receives notification: /topic/driver.5.ride-request


STEP 3 — Driver accepts
────────────────────────
POST /api/ride-requests/{id}/accept?driverId=5
    ↓
Booking created (CONFIRMED)
Passenger notified: /topic/passenger.1.ride-updates → { status: "CONFIRMED" }


STEP 4 — Passenger subscribes to driver location (after CONFIRMED)
────────────────────────────────────────────────────────────────────
client.subscribe('/topic/passenger.1.driver-location', handler)


STEP 5 — Driver sends location every 3-5s
───────────────────────────────────────────
WebSocket /app/driver/location → { driverId:5, lat:28.614, lng:77.210 }
    ↓
findActiveByDriverId(5) → booking found (CONFIRMED)
    ↓
/topic/passenger.1.driver-location → { driverId:5, lat:28.614, lng:77.210 }
Passenger sees driver moving on map


STEP 6 — Driver picks up passenger
─────────────────────────────────────
PATCH /api/bookings/42/status?status=IN_PROGRESS
    ↓
Passenger notified: /topic/passenger.1.ride-updates → { status: "IN_PROGRESS" }
Location tracking continues — booking still active


STEP 7 — Ride completes
─────────────────────────
PATCH /api/bookings/42/status?status=COMPLETED
    ↓
Passenger notified: /topic/passenger.1.ride-updates → { status: "COMPLETED" }
findActiveByDriverId(5) → empty (no active booking)
Location pushes stop automatically


STEP 8 — Driver ends shift
────────────────────────────
POST /api/drivers/5/offline
    ↓
Driver removed from Redis — no longer discoverable
```
