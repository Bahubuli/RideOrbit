# 2. WebSocket Implementation

## What problem does WebSocket solve?

Normal HTTP is request → response. The client always has to ask first:

```
Client:  "is my driver confirmed yet?"   → Server: "no"
Client:  "is my driver confirmed yet?"   → Server: "no"
Client:  "is my driver confirmed yet?"   → Server: "yes"  ← wasted 2 requests
```

WebSocket flips this. After one handshake the connection stays open and the
server can push anytime — no request needed:

```
Client connects once
Server: "your driver is confirmed"    ← server pushes
Server: "your ride has started"       ← server pushes again
```

---

## Why not just use Redis pub/sub for everything?

```
Redis pub/sub  =  server to server communication
WebSocket      =  server to BROWSER communication
```

Redis lives in the server world. A browser has no Redis client, no way to
subscribe to a Redis channel. It is impossible for a browser to talk to Redis directly.

WebSocket is the bridge between the server and the browser:

```
Redis  ──→  Spring App  ──→  WebSocket  ──→  Browser
      (server world)      (the bridge)    (client world)
```

You need both. They solve different problems:

| | Redis pub/sub | WebSocket |
|---|---|---|
| Who uses it | Server talking to server | Server talking to browser |
| Can a browser use it | No | Yes |
| Purpose in this project | Sync events between app instances | Deliver events to the user's browser |

---

## But raw WebSocket has no structure

WebSocket is just an open pipe — raw bytes going back and forth.
No concept of topics, subscriptions, or routing to the right recipient.

That is where **STOMP** comes in.

STOMP (Simple Text Oriented Messaging Protocol) is a thin layer on top of
WebSocket that adds structure:

```
WebSocket  =  roads  (raw infrastructure, just bytes)
STOMP      =  postal system built on top (addresses, routing, delivery)
```

With STOMP a client can say:
```
SUBSCRIBE /topic/booking.5
```

And the server can say:
```
SEND /topic/booking.5  ← only clients subscribed here receive this
```

## File: `WebSocketConfig.java`

```
src/main/java/com/jitendra/RideOrbit/config/WebSocketConfig.java
```

```java
@Configuration
@EnableWebSocketMessageBroker
public class WebSocketConfig implements WebSocketMessageBrokerConfigurer {

    @Override
    public void configureMessageBroker(MessageBrokerRegistry registry) {
        registry.enableSimpleBroker("/topic");
    }

    @Override
    public void registerStompEndpoints(StompEndpointRegistry registry) {
        registry.addEndpoint("/ws").setAllowedOriginPatterns("*");
    }
}
```

There are two methods. They do completely different things.

---

### Method 1 — `registerStompEndpoints`

```java
registry.addEndpoint("/ws").setAllowedOriginPatterns("*");
```

This registers the **URL the browser connects to**.

```
Browser hits  ws://localhost:8080/ws
      ↓
Spring sees the request
      ↓
Upgrades the HTTP connection to WebSocket
      ↓
Browser is now connected, connection stays open
```

Without this the browser has nowhere to connect. This is just the entry point —
one URL, one upgrade, done.

`setAllowedOriginPatterns("*")` — accept connections from any domain.
Lock this to your domain in production.

---

### Method 2 — `configureMessageBroker`

```java
registry.enableSimpleBroker("/topic");
```

This method sets up routing rules for messages AFTER the browser is connected.

This one line does two things:

**1. Starts the in-memory broker**

The broker is a simple message router that lives inside your Spring app.
Its only job:
```
keep a map of who subscribed to what
when a message arrives → look up the map → push to the right clients
```

Think of it like a hotel receptionist with a notepad:
```
Client A connects → "notify me for /topic/booking.5"
Client B connects → "notify me for /topic/booking.5"
Client C connects → "notify me for /topic/booking.99"

Notepad:
  /topic/booking.5  →  [Client A, Client B]
  /topic/booking.99 →  [Client C]
```

**2. Registers `/topic` as the broker's prefix**

The prefix is how Spring decides what to do when a message is sent.

When your server calls:
```java
messagingTemplate.convertAndSend("/topic/booking.5", event)
```

Spring looks at the destination `/topic/booking.5`:
```
does it start with /topic?
    YES → hand it to the in-memory broker
```

The broker receives it, looks up the map, finds Client A and Client B,
pushes the message down their WebSocket connections. Done.

Without the prefix Spring has no idea the broker should handle it and drops the message.

---

## The in-memory broker is NOT Redis

The broker is just a `HashMap` in your app's RAM. No network, no Redis, nothing external.

```
in-memory broker = HashMap inside your Java process
                   { "/topic/booking.5" → [ws connection, ws connection] }
```

---

## Can you use a different broker?

Yes. Spring supports 3 options:

| Broker | How | Good for |
|---|---|---|
| In-memory | `enableSimpleBroker("/topic")` | Dev, single instance |
| RabbitMQ | `enableStompBrokerRelay(...)` | Production, supports STOMP natively |
| ActiveMQ | `enableStompBrokerRelay(...)` | Production, supports STOMP natively |

RabbitMQ and ActiveMQ support STOMP natively — meaning you can completely replace
the in-memory broker AND skip the Redis pub/sub setup.
They handle cross-instance broadcasting themselves.

But since this project already has Redis in the stack, using
Redis pub/sub + in-memory broker is the simpler choice.

## How it all works with multiple instances — full diagram

```
                      PUBLISH SIDE
                      ────────────
                 Booking updated on Instance A
                           │
                           │ publish to Redis
                           ▼
                 ┌─────────────────┐
                 │      REDIS      │
                 │ "booking-events" │
                 └─────────────────┘
                      │         │
           ┌──────────┘         └──────────┐
           │ push to all subscribers       │
           ▼                               ▼
┌──────────────────────┐     ┌──────────────────────┐
│      Instance A      │     │      Instance B      │
│                      │     │                      │
│  onMessage() fires   │     │  onMessage() fires   │
│         │            │     │         │            │
│  messagingTemplate   │     │  messagingTemplate   │
│  /topic/booking.5    │     │  /topic/booking.5    │
│         │            │     │         │            │
│  in-memory broker    │     │  in-memory broker    │
│  looks up its map    │     │  looks up its map    │
│         │            │     │         │            │
│   ┌─────┴─────┐      │     │   ┌─────┴─────┐      │
│   ▼           ▼      │     │   ▼           ▼      │
│ Client 1  Client 2   │     │ Client 3  Client 4   │
│    ✓         ✓       │     │    ✓         ✓       │
└──────────────────────┘     └──────────────────────┘

All 4 clients notified ✓
```

Even though the update happened on Instance A only, all 4 clients are notified because:
- Instance A publishes to Redis
- Redis broadcasts to ALL instances (A and B)
- Each instance's in-memory broker delivers to its own connected clients

```
Redis            → gets the event to the right APP INSTANCE
in-memory broker → gets the event to the right WEBSOCKET CLIENT within that instance
```

## How a client connects

```
client.activate()
        ↓
HTTP GET /ws        (browser asks to upgrade the connection)
        ↓
Server upgrades to WebSocket
        ↓
STOMP CONNECT frame
        ↓
STOMP SUBSCRIBE /topic/booking.5
        ↓
Broker adds to its map: /topic/booking.5 → [this client]
        ↓
Connection stays open — client is now waiting for pushes
```

From [ws-test.html](src/main/resources/static/ws-test.html):

```javascript
const client = new StompJs.Client({ brokerURL: 'ws://localhost:8080/ws' })

client.onConnect = () => {
    client.subscribe('/topic/booking.5', (frame) => {
        const event = JSON.parse(frame.body)
        console.log(event.message)  // "Driver confirmed your booking"
    })
}

client.activate()
```

## How the server pushes to that client — full flow

```
PATCH /api/bookings/5/status?status=CONFIRMED
        ↓
BookingServiceImpl.updateStatus()
        ↓
BookingNotificationService.notifyBookingUpdate(response)
  → builds BookingStatusEvent
  → serializes to JSON
  → publishes to Redis "booking-events"
        ↓
Redis pushes to ALL app instances
        ↓
RedisBookingEventListener.onMessage() fires on each instance
  → messagingTemplate.convertAndSend("/topic/booking.5", event)
        ↓
Spring sees /topic → hands to in-memory broker
        ↓
Broker looks up map → finds subscribed clients
        ↓
Pushes over WebSocket to each client
        ↓
Browser receives:
{
  "bookingId": 5,
  "status": "CONFIRMED",
  "message": "Driver confirmed your booking",
  "passengerId": 1,
  "driverId": 3,
  "timestamp": "2026-03-22T10:30:00"
}
```

## File: `BookingNotificationService.java`

```
src/main/java/com/jitendra/RideOrbit/service/BookingNotificationService.java
```

Called by `BookingServiceImpl` after every create/update.
Does not push to WebSocket directly — publishes to Redis first.

```java
public void notifyBookingUpdate(BookingResponse booking) {
    BookingStatusEvent event = BookingStatusEvent.builder()
            .bookingId(booking.getId())
            .status(booking.getStatus())
            .passengerId(booking.getPassengerId())
            .driverId(booking.getDriverId())
            .message(humanMessage(booking.getStatus()))
            .timestamp(LocalDateTime.now())
            .build();

    String json = objectMapper.writeValueAsString(event); // Java object → JSON string
    redisTemplate.convertAndSend("booking-events", json); // publish to Redis
}
```

The `humanMessage()` maps each status to readable text:

```java
case PENDING     -> "Booking created — waiting for a driver"
case CONFIRMED   -> "Driver confirmed your booking"
case IN_PROGRESS -> "Your ride has started"
case COMPLETED   -> "Ride completed successfully"
case CANCELLED   -> "Booking has been cancelled"
```

## File: `RedisBookingEventListener.java`

```
src/main/java/com/jitendra/RideOrbit/listener/RedisBookingEventListener.java
```

Receives from Redis, calls `messagingTemplate` which hands to the STOMP broker.

```java
@Override
public void onMessage(Message message, byte[] pattern) {
    BookingStatusEvent event = objectMapper.readValue(message.getBody(), BookingStatusEvent.class);
    messagingTemplate.convertAndSend("/topic/booking." + event.getBookingId(), event);
}
```

## Simple summary

```
registerStompEndpoints  →  the door the browser knocks on to connect (/ws)
configureMessageBroker  →  routing rules once the browser is connected
/topic prefix           →  tells Spring "give this to the broker"
in-memory broker        →  HashMap of who subscribed to what, delivers to WebSocket clients
Redis                   →  broadcasts the event to all app instances first
```

```
BookingService
    → NotificationService → Redis → RedisBookingEventListener
                                          → messagingTemplate("/topic/booking.5")
                                                → Spring sees /topic → broker
                                                      → broker finds subscribers
                                                            → pushes to browsers
```
