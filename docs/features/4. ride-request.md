# 4. Ride Request

## What is a Ride Request?

A ride request is what happens before a booking exists.

```
Passenger opens app
    ↓
Enters pickup and dropoff location
    ↓
Taps "Request Ride"
    ↓
System finds nearby drivers (available or on a ride)
    ↓
Notifies them all via WebSocket
    ↓
A driver accepts → booking is created
```

This is the Uber-style flow. The passenger does not pick a specific driver —
they broadcast to everyone nearby and whoever accepts first gets the ride.

---

## How nearby drivers are found — Redis GEO

Driver locations are stored in Redis using a geospatial index.
When a driver updates their location, it gets stored in a Redis sorted set
with the coordinates encoded as a geohash score.

```
Redis key: "driver:location:geo"
Type: sorted set (geospatial index)

Members:
  "5"  → encoded position of driver 5
  "12" → encoded position of driver 12
  "7"  → encoded position of driver 7
```

When a ride is requested, Redis runs `GEORADIUS` server-side:

```
GEORADIUS driver:location:geo  77.2090 28.6139  5 km
    ↓
Redis computes distance from that point to every driver in the set
    ↓
Returns only drivers within 5km, sorted by distance ascending
```

This all happens inside Redis — no loading all drivers into app memory,
no Haversine calculation in Java. Fast, efficient, scales to thousands of drivers.

---

## Online vs Available — two different states

This is the most important concept to understand before reading the availability check.

A driver can be in three possible states:

| State | Meaning | In Redis? |
|---|---|---|
| **Offline** | Driver closed the app | Removed from Redis entirely |
| **Online + Available** | App is open, free to take rides | In Redis, `isAvailable = true` |
| **Online + Unavailable** | App is open, currently on a booking | Still in Redis, `isAvailable = false` |

The third row is the key one. When a driver accepts a ride and picks up a passenger:

- They are **still online** — GPS is still running, location is still updating every 3-5 seconds
- You cannot remove them from Redis because the passenger's app needs to track where the driver is during the trip
- They **can still receive new ride requests** — a driver finishing a ride can accept the next one early

So "remove from Redis" means **went offline**. "Unavailable" means **busy on a ride** but still reachable. These are two different things.

```
Driver accepts booking
    ↓
Still sending GPS every 3-5s → still in Redis geo index
    ↓
isAvailable = false → still included in ride request notifications
    ↓
Driver can accept a new ride even while finishing the current one
    ↓
Driver closes app → removed from Redis entirely
```

---

## How availability is stored — Redis hash flag

Each driver has a hash in Redis alongside their geo entry:

```
Redis key: "driver:location:data:5"
Type: hash

Fields:
  driverId    → 5
  latitude    → 28.6139
  longitude   → 77.2090
  lastUpdated → 2026-03-22T10:30:00
  isAvailable → true              ← this is what the availability check reads
```

`BookingServiceImpl` writes to this flag every time a driver's availability changes:

```
Booking created  → locationService.updateDriverAvailability(driverId, false)
Booking COMPLETED → locationService.updateDriverAvailability(driverId, true)
Booking CANCELLED → locationService.updateDriverAvailability(driverId, true)
```

This means the availability check during a ride request reads one field from one Redis hash — no database query needed.

### Why not just remove from the geo index when unavailable?

Because location updates keep coming. The driver's app sends GPS every 3-5 seconds over WebSocket. `saveDriverLocation()` would re-add the driver to the geo index on every ping — immediately undoing the removal.

The flag approach is correct: keep the driver in geo (location tracking still works), just mark them as unavailable so ride requests skip them.

---

## Who gets notified — online drivers only

`getNearbyDrivers()` filters only one thing: whether the driver is still online.
A driver is considered offline when their data hash has expired (6-hour TTL with no location update).

Drivers currently on a booking (`isAvailable = false`) **are still included** — they get the
notification and can accept if they choose to. The `isAvailable` flag is no longer used to
filter ride request notifications.

```java
// inside getNearbyDrivers() — skip only if data hash has expired (driver went offline)
if (!Boolean.TRUE.equals(redisTemplate.hasKey(dataKey))) {
    continue;
}
// isAvailable is NOT checked here — busy drivers can still accept new requests
```

`getNearbyDrivers()` returns all **online** nearby drivers regardless of their booking status.
No DB query needed — offline detection is a single Redis key existence check.

---

## How drivers are notified — WebSocket

Each driver has their own personal topic:

```
/topic/driver.{driverId}.ride-request
```

Driver 5 subscribes to `/topic/driver.5.ride-request`
Driver 12 subscribes to `/topic/driver.12.ride-request`

When a ride request comes in, we push to each available nearby driver's topic:

```java
messagingTemplate.convertAndSend(
    "/topic/driver." + driverId + ".ride-request",
    notification
);
```

This means:
- Driver 5 only sees requests sent to `/topic/driver.5.ride-request`
- Driver 12 only sees requests sent to `/topic/driver.12.ride-request`
- No driver sees another driver's notifications

The notification goes through RabbitMQ → WebSocket → driver's browser,
same pipeline as booking status updates.

**`RideRequestNotification.java`**
```
src/main/java/com/jitendra/RideOrbit/dto/RideRequestNotification.java
```
What each nearby available driver receives over WebSocket:
```json
{
  "rideRequestId": "f3a2c1d0-...",
  "passengerId": 1,
  "passengerName": "Rohan",
  "pickupLatitude": 28.6139,
  "pickupLongitude": 77.2090,
  "pickupAddress": "Connaught Place, Delhi",
  "dropoffLatitude": 28.5355,
  "dropoffLongitude": 77.3910,
  "dropoffAddress": "Noida Sector 18",
  "distanceToPickup": 1.3,
  "timestamp": "2026-03-22T10:30:00"
}
```

`distanceToPickup` comes directly from Redis — how far the driver currently
is from the passenger's pickup point.

`rideRequestId` is a UUID. All drivers notified for the same request share
the same ID so they can reference it when accepting.

```
src/main/java/com/jitendra/RideOrbit/dto/RideRequestResponse.java
```

```json
{
  "rideRequestId": "f3a2c1d0-...",

```

`status` is either:
- `SEARCHING` — at least one driver was notified, waiting for acceptance
- `NO_DRIVERS_FOUND` — no available drivers within 5km

### Service

**`RideRequestServiceImpl.java`**
```
src/main/java/com/jitendra/RideOrbit/service/impl/RideRequestServiceImpl.java
```

Core logic step by step:

```java
// Step 1 — validate passenger
Passenger passenger = passengerRepository.findById(request.getPassengerId())
        .orElseThrow(...);

// Step 2 — find nearby drivers from Redis GEO (5km radius)
List<DriverLocationResponse> nearbyDrivers = locationService.getNearbyDrivers(
        request.getPickupLatitude(),
        request.getPickupLongitude(),
        5.0
);

// Step 3 — generate unique ride request ID
String rideRequestId = UUID.randomUUID().toString();

// Step 4 — notify each driver returned by getNearbyDrivers()
//    The list is already filtered — getNearbyDrivers() skips offline
//    and unavailable drivers while reading the Redis hash per driver.
for (DriverLocationResponse nearbyDriver : nearbyDrivers) {

    RideRequestNotification notification = RideRequestNotification.builder()
            .rideRequestId(rideRequestId)
            .passengerName(passenger.getName())
            .distanceToPickup(nearbyDriver.getDistanceFromPoint())
            ...
            .build();

    messagingTemplate.convertAndSend(
            "/topic/driver." + nearbyDriver.getDriverId() + ".ride-request",
            notification
    );
}
```

## Driver client — how to subscribe

On the driver's side, the browser connects and subscribes to their own topic:

```javascript
const client = new StompJs.Client({ brokerURL: 'ws://localhost:8080/ws' })

client.onConnect = () => {
    // subscribe to your own ride request topic
    client.subscribe('/topic/driver.5.ride-request', (frame) => {
        const request = JSON.parse(frame.body)

        console.log(`New ride request from ${request.passengerName}`)
        console.log(`Pickup: ${request.pickupAddress}`)
        console.log(`Dropoff: ${request.dropoffAddress}`)
        console.log(`You are ${request.distanceToPickup} km from pickup`)

        // show accept / decline UI
    })
}

client.activate()
```

## What happens after a driver accepts?

See **[5. Ride Acceptance and Booking Cleanup](5.%20ride-acceptance-and-booking-cleanup.md)**.

The driver calls `POST /api/ride-requests/{rideRequestId}/accept?driverId=5`.
The system looks up the stored ride request, creates a booking, notifies the
passenger, and dismisses the other drivers — all in one step.
